# DFRobot C4001 SEN0609 to ESP32-C3 integration

Status: physical UART capture verified at 9600 baud with valid `$DFHPD` and
`$DFDMD` reports; live presence and separated live-range targets implemented.

This path is independent of the RD-03D path. It uses the same C3 UART pins so
only one radar module may be attached at a time.

## Identified module

The five labels `VIN`, `GND`, `TX`, `RX`, and `OUT` match DFRobot SKU SEN0609,
the 25 m C4001 UART module. Follow the physical silkscreen labels; do not infer
pin order from cable colors or an unverified photograph.

Official SEN0609 documentation specifies:

- VIN accepts 3.3 V or 5 V.
- The current product wiki and official Arduino library use 9600 baud, 8-N-1.
- DFRobot's protocol PDF also contains a conflicting 115200-default statement,
  but this physical unit has been verified at 9600 baud. Firmware is fixed at
  9600 and does not probe alternate rates.
- UART reports are ASCII, beginning with `$` and ending with `*`.
- Presence mode reports `$DFHPD,...*`.
- Distance/speed mode reports `$DFDMD,...*` and supports one target.
- `OUT` is the presence/control voltage output; default presence polarity is
  high for a detected target and low for no target.

The capture and live firmware send no commands. They do not change mode, baud
rate, sensitivity, range, delays, polarity, or saved configuration.

## Initial wiring

Power down the C3 and sensor before changing wires. Disconnect the RD-03D if it
is attached.

Recommended initial 3.3 V bench:

```text
C4001 VIN -> C3 3V3, after verifying the rail remains approximately 3.3 V
C4001 GND -> C3 GND
C4001 TX  -> optional 47-100 ohm series resistor -> C3 GPIO4
C4001 RX  -> disconnected
C4001 OUT -> C3 GPIO5 (optional when VIN is 3.3 V)
```

`OUT` is not required for UART capture. It may be configured as a static level
or PWM, so firmware samples GPIO5 only alongside reports and does not attach an
edge interrupt to it. UART `$DFHPD` reports remain the authoritative presence
source.

If the C3 regulator cannot supply the module stably, use a separate regulated
3.3 V source and join its ground to C3 ground. Do not join independently
powered positive rails.

The module also supports 5 V VIN. When using 5 V, leave `OUT` disconnected
until its high level has been measured at no more than 3.3 V relative to the
common ground. UART TX is documented for direct ESP32 use, but no ESP32-C3 GPIO
may be exposed to a 5 V signal.

The existing C3-to-S3 link remains unchanged:

```text
C3 GPIO21 TX -> S3 GPIO41 RX
S3 GPIO42 TX -> C3 GPIO20 RX
C3 GND       -> S3 GND
```

## Capture target

```powershell
pio run -e c3-c4001-capture-rdp
pio run -e c3-c4001-capture-rdp -t upload --upload-port COM_NUMBER
pio device monitor -e c3-c4001-capture-rdp --port COM_NUMBER --baud 115200 --dtr 0 --rts 0
```

Normal monitoring is quiet by default. It prints one event when UART presence
changes to detected; clear transitions and periodic status are suppressed.
Type `c` to arm 32 raw reports, `q` to pause raw output, or `v` to toggle full
presence/link/system diagnostics. The UART remains fixed at the verified 9600
baud from startup.

Expected output in presence mode:

```text
[c4001.presence] state=detected out_sample=1
```

With raw capture (`c`) or verbose diagnostics (`v`) enabled, the corresponding
`[c4001.raw]`, `[c4001.status]`, link, and system lines are also printed.

Distance/speed mode instead produces lines shaped like:

```text
[c4001.raw] report=1 out_sample=1 data=$DFDMD,1,1,1.817,0.129,15304, , *
```

Either family is a successful raw-capture result. The sensor's current saved
mode determines which one appears. `link frames=0` is intentional because the
capture target never publishes interpreted `RadarFrame` snapshots. Select one
of the live targets below after the raw stream has been identified.

Use the UART byte and parser counters for diagnostics:

```text
raw_rx_bytes=0
    GPIO4 sees no sensor activity: check sensor power, common ground, TX-to-GPIO4,
    and whether active UART reporting is disabled.

raw_rx_bytes increasing, recognized=0
    Bytes are arriving but are not a documented active report. Preserve the log;
    the unit may use another stored baud/output mode or be sending command text.

recognized increasing, valid_seen=yes
    Electrical and serial capture gates pass.
```

GPIO4 is owned exclusively by the hardware UART. Do not attach a diagnostic
edge interrupt to it; doing so adds interrupt load to every received data bit.

To distinguish sensing from OUT wiring, compare the event fields. If
`state=clear` and `out_sample=0`, the radar itself has not declared presence. If
`state=detected` while `out_sample=0`, investigate OUT wiring, voltage,
configured polarity, or PWM phase. A single `out_sample` is diagnostic only.

Capture batches for no target, a stationary person, approach/retreat, and an
OUT transition if GPIO5 is connected.

## Live presence display target

Keep the same sensor and C3-to-S3 wiring. The S3 runs the existing scanner
display target, while the C3 runs the new live C4001 target:

```powershell
pio run -e s3-scanner-display-rdp
pio run -e s3-scanner-display-rdp -t upload --upload-port S3_COM_NUMBER

pio run -e c3-c4001-live-rdp
pio run -e c3-c4001-live-rdp -t upload --upload-port C3_COM_NUMBER
pio device monitor -e c3-c4001-live-rdp --port C3_COM_NUMBER --baud 115200 --dtr 0 --rts 0
```

The live path accepts only the exact observed presence reports:

```text
$DFHPD,0, , , *
$DFHPD,1, , , *
```

All malformed sentences and distance-mode `$DFDMD` reports are rejected. Two
consecutive equal reports are required to establish initial state and change
state; this prevents a single corrupted ASCII `0`/`1` byte from flipping the
display. Valid reports then publish canonical healthy presence-only frames.
The descriptor advertises only `kPresence`, a 16 m presence envelope, 100°
horizontal field of view, and zero contacts.

Expected C3 evidence:

```text
[c4001] valid presence report; baud=9600
[c4001.live] presence=clear sequence=... out_sample=...
[link] connected=yes ... frames=<increasing> ...
[radar] mode=c4001-live ... valid_presence=<increasing> ...
```

Expected S3 evidence:

```text
[scanner] ... firmware=c3-c4001-live radar=c4001/presence caps=00000001 max_contacts=0 ...
[runtime] state=presence-only ...
[link] connected=yes ... frames=<increasing> ... presence=clear|detected contacts=0 ...
```

The display shows `AREA CLEAR` or `PRES DETECT` with the presence-only radar
presentation. It intentionally shows no contact dots because `$DFHPD` provides
neither range nor position. If valid frames stop arriving, the existing S3
arrival-time policy changes the presentation to stale without inventing a
clear state.

## Live range display target

When the sensor is already producing `$DFDMD` distance/speed reports, retain
the same wiring and keep the S3 on `s3-scanner-display-rdp`. Flash this target
on the C3:

```powershell
pio run -e c3-c4001-range-live-rdp
pio run -e c3-c4001-range-live-rdp -t upload --upload-port C3_COM_NUMBER
pio device monitor -e c3-c4001-range-live-rdp --port C3_COM_NUMBER --baud 115200 --dtr 0 --rts 0
```

The target is read-only: C4001 RX and GPIO5 OUT are not required, and it does
not change the sensor's saved mode. It accepts strict `$DFDMD` reports, requires
two matching target-count reports before creating or clearing a contact, and
publishes each subsequent valid measurement over the normal C3/S3 link.

The C4001 supplies range, radial velocity, and energy but no bearing. The S3
therefore renders one contact at the measured distance on the forward
centerline. This is an explicit unknown-bearing range-only presentation, not a
measured X/Y position. Raw energy can exceed the canonical 16-bit signal field;
only that diagnostic value is saturated at 65535. Range and signed velocity
retain their measured values.

Expected C3 evidence:

```text
[c4001] valid range report; baud=9600
[c4001.range] contacts=1 range_mm=430 velocity_mm_s=197 signal=65535
[link] connected=yes ... frames=<increasing> ...
[radar] mode=c4001-range-live ... valid_range=<increasing> ... contacts=1 range_mm=...
```

Expected S3 evidence:

```text
[scanner] ... firmware=c3-c4001-range radar=c4001/range caps=00000012 max_contacts=1 ...
[runtime] state=range-only ...
[link] connected=yes ... frames=<increasing> ... contacts=1 ...
```

If the sensor emits `$DFHPD` instead, this target increments `unsupported` and
sends no frames. Use `c3-c4001-live-rdp` for presence mode. The direct-S3 setup
target remains available if the sensor's saved report mode must be changed.

For a temporary test that bypasses the C3 without replacing the intended
architecture, use the isolated direct-S3 target documented in
[`c4001-direct-s3.md`](c4001-direct-s3.md).
